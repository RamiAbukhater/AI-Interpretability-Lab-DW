Role-play responses and LLM judges

To find where a persona lives inside the model, we first need text of the model actually playing that persona. This page covers how the notebook produces those responses and how it uses a second model, a judge, to check they really are in character.

The big idea

The plan is to ask the model to play each persona, record what happens inside it while it does, and compare. That only works if the model did play the persona. Instruction-tuned models often half-refuse: "As an AI, I don't have ghostly memories, but here's some advice…". A response like that is mostly the Assistant talking, and if we averaged it into the "ghost" data we would blur the very difference we are trying to measure.

So there are two jobs. First, generate a response for every persona and question pair. Second, judge each response: did the model fully take on the role? Reading hundreds of responses by hand is slow and inconsistent, so we hand the job to another language model with a clear rubric. This is an LLM judge (also called an autorater). It is the same idea as a TA grading with a rubric, except the TA is a model, so it is fast and cheap, and consistent as long as the rubric is clear.

Responses that score below "fully in character" are dropped before we compute anything. Fewer, cleaner examples beat more, muddier ones.

Where the responses come from

There are two options, and the notebook supports both through the GENERATION_BACKEND flag.

  • An API ("openrouter"). The original ARENA notebook sends every persona and question to Gemma 2 27B over OpenRouter. Generating hundreds of answers token by token on your own GPU is the slowest part of the pipeline. An API runs many requests in parallel on someone else's hardware, and your GPU is only needed afterwards to read activations. But OpenRouter no longer serves Gemma 2 9B or 2B, so in our notebook this option means 27B writes the text.
  • Locally ("local", our default). The loaded Gemma 2 9B writes its own responses on Kaggle's GPUs, in batches. This is slower but keeps everything consistent: the text we analyse was written by the very model whose activations we read.

Why does that consistency matter? Activations are recorded by feeding text through our model. If 27B wrote the text, we are measuring how 9B reads a ghost's answer, not how 9B acts as a ghost. That is usually close, but it is not the same experiment, so the notebook defaults to GENERATION_BACKEND = "local". With 9B on Kaggle's T4s the 265 workshop responses take a few minutes. The judge, in contrast, always runs through the API (Claude Haiku, anthropic/claude-haiku-5.5), because it needs to be a different and stronger model.

How it connects to the paper

  • Section 2.1.1 describes the paper's data generation. Every response was labelled by an LLM judge (the paper used gpt-4.1-mini) on this same four-level scale: 0, a clear refusal; 1, says it cannot be the role but still helps; 2, identifies as itself but shows some of the role's attributes; 3, fully plays the role.
  • The paper builds role vectors only from responses that sufficiently express the role, and requires a minimum number of such responses per role.
  • The paper's repository keeps per-role judge prompts in data/roles/instructions/; the file for pirate.json is a good example of how detailed a rubric can be.

The notebook keeps the scale but makes the filter optional (RUN_JUDGE_FILTER, off by default) to save API calls and time. With the filter off, every non-empty response is used, which slightly blurs the persona vectors. Turning it on is a good extension.

  • One function, two routes. generate_responses_parallel checks its model argument: the special value "local" sends the conversations to the loaded Gemma, and anything else is treated as an OpenRouter model name. Persona generation uses the default (OPENROUTER_MODEL, which is "local" unless you change GENERATION_BACKEND); the judges pass their own model name.
  • A conversation is a list of message dictionaries such as {"role": "user", "content": "..."}. messages_list is a list of conversations, one per response.
  • Local batching. Prompts are sorted by length and generated GEN_BATCH_SIZE at a time (32 on 9B). Padding goes on the left so every prompt ends right where generation starts. Generation stops at Gemma's <end_of_turn> token. If you run out of GPU memory here, lower GEN_BATCH_SIZE.
  • API calls run MAX_WORKERS at a time (4) in threads. More workers is faster until you hit a rate limit (HTTP 429); then lower it.
  • API errors are caught and turned into an empty string "", so one failed call does not crash a run. That is why later code skips empty responses. It also means a bad key or no credit shows up as a stream of printed API error lines, not as one crash, so read the output.
  • temperature=0.7 for persona responses (some variety); the judges use temperature=0.0 so the same response always gets the same score.

def judge_role_response(question, response, character,

    judge_response = generate_responses_parallel(

What you write: a prompt template and a parser. judge_role_response is provided and glues them together.

TemplateA string with the placeholders {question}, {response}, and {character}. It must explain the 0 to 3 scale and ask for the score in a fixed, machine-readable format.
parse_scoreTakes the judge's raw reply (a string) and returns an int from 0 to 3. It should fail loudly if it cannot find a score.
Hint 1: the format

Ask for the score wrapped in tags, such as <score>2</score>, and include an example of the exact output you want in the prompt. Language models follow examples more reliably than descriptions.

Hint 2: the parser

A regular expression that only accepts the digits 0 to 3 inside your tags does the job. Use re.search, and raise or assert if there is no match rather than silently returning 0, since a silent 0 would quietly throw data away.

Hint 3: the rubric wording

Name the character in the prompt ("how well did the model role-play as the character '{character}'?") and spell out all four levels. Vague levels like "pretty good" give inconsistent scores.

Filtering with the scores

Your generation function from the exercise above is then run on every persona and question. Responses are saved to CACHE_DIR/responses.json, and only personas missing from that file get generated, so re-running is cheap. Next, if you set RUN_JUDGE_FILTER = True at the top of the notebook, the provided cell below scores every response with your judge before activations are extracted:

scores: dict[tuple[str, int], int] | None = None
if RUN_JUDGE_FILTER:
    SCORES_PATH = CACHE_DIR / "judge_scores.json"
    scores = {(p, q): s for p, q, s in json.loads(SCORES_PATH.read_text())} if SCORES_PATH.exists() else {}
    to_score = [k for k, r in responses.items() if r and k not in scores and k[0] not in DEFAULT_PERSONAS]

    def _score(key):
        try:
            return key, judge_role_response(question=EVAL_QUESTIONS[key[1]], response=responses[key], character=key[0])
        except Exception as e:  # unparseable judge output counts as a fail
            print(f"Judge failed for {key}: {e}")
            return key, 0

    with ThreadPoolExecutor(max_workers=MAX_WORKERS) as executor:
        for key, score in tqdm(executor.map(_score, to_score), total=len(to_score)):
            scores[key] = score
    SCORES_PATH.write_text(json.dumps([[p, q, s] for (p, q), s in scores.items()]))
    scores |= {(p, q): 3 for p in DEFAULT_PERSONAS for q in range(len(EVAL_QUESTIONS))}  # never filter defaults
  • The keys are (persona, question_index) pairs, the same keys as responses. Already-scored responses are loaded from judge_scores.json, so the API is only called for new ones.
  • Responses are judged in parallel, MAX_WORKERS at a time. A judge reply that cannot be parsed counts as 0, so it is filtered out rather than crashing the run.
  • The default personas are never filtered: they get a 3 automatically. They have no role to play, so a judge asking "did it play the role?" would be meaningless for them.
  • The scores dictionary then goes into extract_persona_vectors (concept 3), which skips any response below score_threshold=3. A persona with no surviving responses is skipped entirely, with a message.

With the filter off (the default) scores stays None and every non-empty response is used. For the 265 workshop responses, the filter costs a few minutes and well under a dollar of OpenRouter credit.

Check your understanding

Q1.Why filter out responses that score 1 or 2 instead of keeping everything?

Those responses are partly the Assistant talking ("As an AI I can't really…"). Including them pulls each persona's average toward the Assistant and shrinks the differences we want to measure. Keeping only score-3 responses gives a cleaner signal of the role itself.

Q2.The judge runs at temperature 0. Why?

Temperature 0 makes the judge (nearly) deterministic, so the same response gets the same score every time. A grader should be consistent; creativity is not wanted here.

Q3.If responses are generated by Gemma 2 27B through the API but activations are read from Gemma 2 9B, what are we actually measuring?

How 9B represents text that a different model wrote in character, which is close to but not the same as how 9B represents itself acting in character. That is why the notebook defaults to local generation with the same model.

Q4.Why should parse_score raise an error instead of returning 0 when it cannot find a score?

Returning 0 would silently mark the response as a refusal and throw it away. If the judge's output format breaks, you want to find out immediately, not end up with suspiciously empty persona data.

Common mistakes

  • Not noticing printed API error lines. Failed calls return empty strings. A wrong key (401) or no credit (402) shows up as many errors and many empty responses, not as a crash.
  • Using a retired judge model. Model names change. If you see "No endpoints found", check openrouter.ai/models.
  • Mismatched placeholders. If your template uses {role} but the code calls .format(character=...), Python raises a KeyError. Any literal curly braces in the template (for example in a JSON example) must be doubled: {{ }}.
  • Setting MAX_WORKERS high to go faster and getting 429 rate-limit errors. Moderate parallelism is faster overall.
  • Keys that do not line up. The response dict, the scores dict, and the loop in extract_persona_vectors must all use (persona_name, question_index) with the question's index, not the question text.
