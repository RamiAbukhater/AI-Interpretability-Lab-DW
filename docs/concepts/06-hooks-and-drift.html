PyTorch hooks and monitoring persona drift

With the Assistant Axis in hand we can use it as a gauge. This page shows how to read the model's activations in the middle of a forward pass with a hook, and how to track a whole conversation turn by turn to see whether the model is drifting out of its Assistant role.

Content note

Section 2 uses real case-study transcripts from the paper's repository, including conversations where a model validates a user's delusions or responds badly to someone in distress.

The big idea

Hooks: a tap on the pipe

The simplest way to see inside the model is to ask for all hidden states with output_hidden_states=True. That keeps 43 copies of the residual stream in memory at once (the embeddings plus one per block), which is fine for a short response but wasteful for a conversation thousands of tokens long on a 15 GB T4. We only want one layer. That is why the notebook uses hooks everywhere, starting with Section 1's extract_response_activations.

A forward hook is a function you attach to one module (here, one transformer block). Every time that module finishes its forward pass, PyTorch calls your function with the module, its input, and its output. Your function can store the output somewhere (to read it) or return a modified version (to change what the rest of the model sees). It is a tap fitted to one point in the pipe: water flows past as usual, but you can sample it, or add something to it, right there. The hook stays attached until you remove it, so you always remove it in a finally block.

Drift: where is the model on the axis, turn by turn?

The Assistant Axis points from "role-playing" toward "default Assistant". If we take the model's activations during one assistant turn of a conversation, average them over that turn's tokens, and project onto the axis, we get one number: how Assistant-like the model was in that turn. Doing this for every turn gives a trajectory. A flat trajectory means the model stayed itself. A trajectory that falls means the conversation pulled it away from the Assistant, which the paper calls persona drift.

\[ p_k = \bar h_k \cdot a, \qquad \bar h_k = \frac{1}{|T_k|}\sum_{t \in T_k} h_t^{(\ell)}, \]

where \(T_k\) is the set of token positions of assistant turn \(k\) and \(a\) is the unit-length Assistant Axis. The values are raw dot products, so for Gemma 2 they are large (hundreds to thousands). Only the change across turns matters, not the absolute number.

To see whether drift lines up with bad behaviour, the notebook also has an LLM judge rate each assistant turn for how much it reinforces a user's delusions. If the axis means what we think it does, the projection should go down as the risk score goes up.

How it connects to the paper

  • Section 4, "Persona dynamics and persona drift", projects middle-layer activations, averaged over the tokens of each turn, onto the axis across multi-turn conversations.
  • Section 4.1 and Figure 7: coding and writing conversations stay in the Assistant range, while therapy-like conversations and philosophical discussions about AI's own nature drift toward the non-Assistant end.
  • Section 4.3 links drift to undesirable behaviour, and Section 6.2 is the delusion case study whose transcripts we use. The paper's README figure (right panel) shows exactly this kind of per-turn trajectory.
  • Sections 5 and 6 then cap activations along the axis to prevent drift. Capping is out of scope for us, but the notebook does show a transcript from the capped model for comparison.

Finding the transformer blocks

def _return_layers(m) -> list:
    """Walk model attributes to locate the list of transformer blocks."""
    for attr_path in ("language_model.layers", "layers"):
        obj = m.model
        try:
            for name in attr_path.split("."):
                obj = getattr(obj, name)
            return obj
        except AttributeError:
            continue
    raise AttributeError(f"Could not find transformer layers on {type(m)}")

Hooks attach to modules, so we need the list of decoder blocks. For Gemma 2 it is model.model.layers, a list of 42 blocks. The helper also handles models that nest it one level deeper.

A minimal hook, and what KV caching does to it

test_prompt = "The quick brown fox"
test_tokens = tokenizer(test_prompt, return_tensors="pt").to(model.device)

def hook_fn(module, input, output):
    print(f"Hook captured shape: {_get_hidden(output).shape}")

hook = _return_layers(model)[EXTRACTION_LAYER].register_forward_hook(hook_fn)
try:
    with t.inference_mode():
        _ = model.generate(**test_tokens, max_new_tokens=3)
finally:
    hook.remove()
  • _get_hidden(output) unwraps the block's output, which is a tensor in recent transformers versions and a tuple in older ones.
  • register_forward_hook attaches hook_fn to one block and returns a handle. hook.remove() in finally detaches it even if generation crashes. A forgotten hook stays on the model and silently affects every later call.
  • The first call prints (1, prompt_len, d_model): the whole prompt is processed at once.
  • Each later call prints (1, 1, d_model). With KV caching, the model stores each earlier token's attention keys and values and only runs the newest token through the stack. So during generation, the hook sees one token at a time.

Turn spans

The provided utils.get_turn_spans(messages, tokenizer) returns a list of (start, end) token positions, one per assistant message. For the assistant message at index \(i\), it formats messages[:i] with the generation prompt (where the reply starts) and messages[:i+1] without it (where the reply ends). The notebook prints the first tokens of each span so you can see that they line up.

        raise NotImplementedError()

    def project_onto_axis(self, messages) -> list[float]:
        """Project each assistant turn's mean activation onto assistant_axis."""
        raise NotImplementedError()

What it must do: compute one projection per assistant turn with a single forward pass over the whole conversation. Running one pass per turn would reprocess the start of the conversation again and again, costing time proportional to the square of its length.

Hint 1: capturing the output

Make an empty dict outside the hook function. Inside the hook, store output in it. Register on _return_layers(self.model)[self.layer], run self.model(**tokens) once under inference_mode, and remove the hook in finally.

Hint 2: tokenizing

Use apply_chat_template(..., tokenize=False, add_generation_prompt=False) on the full message list, then tokenize with add_special_tokens=False, so positions match the spans from get_turn_spans.

Hint 3: projecting

Convert each turn mean and the axis to CPU float32, then take the dot product and call .item(). Free the captured tensor and call t.cuda.empty_cache() before returning; long transcripts are large.

    Returns:
        Delusion risk score (0-100, lower is better)
    """
    raise NotImplementedError()

What it must do: fill in the provided AUTORATER_PROMPT_TEMPLATE with the conversation so far and the assistant message at latest_asst_idx, send it to the judge model through OpenRouter, parse the two 1-to-5 scores it returns (avoiding delusional amplification, and normalising rather than exceptionalising), and turn them into a 0 to 100 risk score.

Both scores are "higher is safer", so risk is how far below the maximum they are, rescaled:

\[ \text{risk} = 100 \cdot \frac{1}{2}\sum_{j=1}^{2} \frac{5 - s_j}{5 - 1}. \]

Two 5s give 0 (safe); two 1s give 100.

Hint 1

Build the history as plain text, one line per message, up to and including latest_asst_idx. The template has {history} and {latest_response} placeholders.

Hint 2

The template asks for XML tags. A single regular expression with a back-reference, matching an opening tag, its content, and the same closing tag, can pull out both values at once. Check that you got exactly the two expected tag names.

Hint 3

Call the judge at temperature 0 using the same generate_responses_parallel helper as the role-play judge. Give it plenty of tokens, about 1200: claude-haiku-5.5 thinks before it answers, and with 200 tokens the reply can come back empty (the helper prints finish_reason='length'). The notebook's sanity check asserts that a delusion-validating reply scores higher than a grounding one.

A subtlety worth noticing

These transcripts were written by Llama 3.3 70B in the paper, not by Gemma. When we run them through Gemma and read its activations, we are measuring how Gemma represents that conversation, not how Gemma would have behaved in it. That the projection still tracks the risk score suggests the axis captures something about the text's persona, not just one model's own state.

Check your understanding

Q1.What three arguments does a forward hook receive, and how can it change the model's computation?

The module, its input, and its output. If the hook returns a value, that value replaces the module's output for the rest of the forward pass. Returning nothing leaves the output unchanged.

Q2.Why does the hook see shape (1, 1, d_model) after the first step of generate?

Because of KV caching. After the first pass over the prompt, the model reuses cached keys and values for earlier tokens and only passes the single newest token through the layers.

Q3.Why compute every turn from one forward pass instead of one pass per turn?

A causal model's activation at a token depends only on earlier tokens, so one pass over the full conversation already contains each turn's activations exactly as they would be in a shorter pass. Separate passes would redo the shared beginning many times, which is far slower for long conversations.

Q4.The projections are in the thousands. Is something wrong?

No. They are dot products of raw activations, whose norm at this layer is large in Gemma 2, with a unit vector. Only the trend across turns, and comparisons between transcripts at the same layer, are meaningful.

Q5.What sign do you expect for the correlation between projection and delusion risk, and why?

Negative. The axis points toward the Assistant, so lower projection means further from the Assistant persona, which should coincide with the model going along with the user's delusions, a higher risk score.

Common mistakes

  • Not removing a hook. Always use try / finally. A leftover capturing hook leaks memory; a leftover steering hook silently changes every later result. If in doubt, restart the session.
  • Skipping _get_hidden. In some versions of transformers, decoder layers return a tuple whose first element is the hidden states. If you see 'tuple' object has no attribute 'shape', you used output directly; wrap it in _get_hidden(output).
  • Hooking a different layer from Section 1. The analyzer must use EXTRACTION_LAYER, the same block the axis was built from. Projecting block-20 activations onto a block-27 axis mixes two different coordinate systems.
  • Out of memory on long transcripts. Lower MAX_DRIFT_TURNS, and keep only the slices you need on the GPU.
  • Reading absolute projection values as meaningful, or comparing them with the paper's Llama numbers. Compare shapes and trends.
